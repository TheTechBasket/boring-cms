Boring CMS Bench

v0.11.0 on a simulated 5-10 USD VPS: taskset-pinned cores, 768 MB heap cap, fresh temp SQLite per run, loopback HTTP. 19 phases, ~2600 requests per run, zero errors across all 9 runs.

Throughput by phase

Operations per second per benchmark phase, one bar per runtime. Hover a bar for latency percentiles. vCPU count barely moves the numbers: the server is single-threaded by design.

Requests vs CPU and memory

Server process sampled every ~100 ms over the whole run (boot, bootstrap, then the 19 phases as shaded bands). CPU is derived from /proc utime+stime deltas; above 100% means more than one core busy. Move the pointer across a panel to read phase, CPU and RSS at that instant.

All numbers

ops/s with p50/p95 latency in ms, at the selected vCPU count.

Constraints (why the numbers look this way)
  • Fresh temp data dir per run: every number includes cold SQLite caches; no run touches another's state.
  • CPU pinning via taskset is an upper bound on a real shared VPS; heap capped at 768 MB (node/deno --max-old-space-size, bun --smol).
  • Client is an unpinned Node process on loopback; network latency is effectively zero, so figures measure the server, not the wire.
  • Per-key rate limit raised from the 60/min default so the bench measures the server, not the limiter.
  • S3 media excluded (costs money); local disk storage tested end to end.
  • Suite lives in bench/ in the repo; re-run with bash bench/run.sh after each release for comparable sets.
